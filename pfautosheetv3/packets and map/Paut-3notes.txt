NEW REQUIREMENT - INGESTION SHOULD PRODUCE FOUR OUTPUTS (Austin, 5:20 PM)
----------------------------------------------------------------------
When a sheet or SRD is ingested it should produce:
  (1) a TABLE (structured, e.g. class progression grids)
  (2) a LIST OF LINKS
  (3) a COMPACT MARKDOWN, text only
  (4) an INDEX for AI lookups, made of keywords that appear frequently or prominently
How that maps to today's code:
  (1) Table
      APP today: only class grids, by regex (sotEngine.ts extractClassFromSrdDoc,
      parseClassProgressionGrid). Fixed 7-column ClassGridRow, so extra columns are lost into
      "special". Other tables (spells per day, talents, items) are not extracted.
      LAZY\sheet-engine: src\ingest\tables.ts. Any <table>, with rowspan/colspan expanded and
      multi-row headers joined -> tables.json (caption, columns, rows, raw cells). On armorist HTML
      it found 2 tables.
  (2) Links
      APP today: sanitizeSrdDocument collects incidentalLinks (142 on armorist), but it also turns
      every <a> in htmlContent into a <span>, so link positions are lost.
      LAZY: links.json (text, href, canonical-resolved, section_id). It got 0 links on armorist
      because I fed it APP's already-sanitized HTML. It must ingest the ORIGINAL HTML, or rebuild
      links from incidentalLinks.
  (3) Compact markdown
      APP today: plainText (tags stripped, tables as tabs, not markdown, not de-duplicated).
      LAZY: Turndown markdown, split into heading-aware sections (sections.jsonl), with tables
      replaced by "[Table: caption; table_id=...]" placeholders. Measured on armorist: about 49.5k
      estimated tokens -> about 11.2k (-77%).
  (4) Keyword index
      APP today: none. Macaroni suggestions are not an index, and the whole SOT goes to the model.
      LAZY: src\ingest\keywords.ts adds keywords per section from heading, defined terms
      (<strong>/<b>/<dt>/<dfn>), table headers, frequent terms, a field dictionary and synonyms ->
      keywords.json. Plus a MiniSearch BM25 index (index.json) and a table of contents (toc.json).
      This is close to "frequently or prominently" already.
  Gaps to close:
   - sheet-engine skips .json, so .srd.json needs an unwrap step (srdDocument.htmlContent ->
     .html), and sheets (character.json / _pf1e_sheet.json) need their own small extractor.

   - Where outputs live (PROPOSAL, nothing like it exists yet): the save tree's unused SRD folder,

CHARACTER MATRIX / CAREER INDEX / USER INDEX OVERHAUL - CLARIFICATIONS AND PREDICTIONS
----------------------------------------------------------------------
What it replaces (current components):
- ClassArchitectModal.tsx career tab: careerData (CareerProgressionData: mode
  standard/multiclass/gestalt, levels[] of CareerLevelEntry with primary plus 1 gestalt),
  handleAdd/Remove/UpdateCareerLevel, handleSyncCareerToSheet ->
  characterIntegration.ts applyCareerProgressionToCharacter -> multiclassCalculator.ts
  calculateCareerProgression.
- Class 1 / class 2 grid subtabs: character.customClassGrids (a record of CustomClassGrid with
  ClassGridRow[] rows), handleAddNewClass / handleDeleteClass (with the id-collision bug above),
  and the "+ Add Class" tab position.
- The mode toggles (multiclass / gestalt / variant multiclassing) become notation in the Career
  Index (commas, a second track column, * dominance).
- handleAddKit's HD/HP/skills/proficiencies writes become "Apply matrix to sheet".
- Orphaned AddClassModal.tsx should be deleted, not ported.
Data-model implications:
- The grid has to become generic: {columns: [{id, header, type: number|text|ability-list,
  frozen?, hidden?}], rows: Record<colId, value>[], row0?}. ClassGridRow's fixed fields can't
  hold arbitrary columns. Existing customClassGrids need a migration (level/bab/fort/ref/will/
  special -> named columns).
- Career Index = {tracks: [{header, cells: string[]}]}. Each cell is a parsed token list
  (className, explicit count, +col/-col/=col filters, * dominance, comma gestalt).
- The matrix is DERIVED. It should be recomputed from the Career Index plus user indexes, not
  stored as truth, or the two will drift. Applying to the sheet is a separate explicit action.
- "Same columns combine" needs a column-identity rule (header normalization: "Base Attack Bonus"
  = "BAB"). Numeric merge rules per column type: gestalt within a cell takes the FIRST value as
  dominant; a second track takes the HIGHER value. The text in the spec says exactly that.
- Ability tags <act>/<rec>/<spell>/<feat> map onto characterActions types, resourceTrackers,
  spells and characterFeats. Today abilities synced via syncCareerAbilitiesToDirectory come in as
  actions/resources with no way to change type afterward. The "make it editable" ask touches
  ActionDirectoryModule.tsx.
- Row 0 (race) writes outside the level sequence (raceMod, traits) and is not shown on the matrix.
- assign / auto-assign link an index cell to a text block in the SOT, which needs the ingestion
  index (four outputs above) to have stable section ids. sheet-engine's section_id is a fit.
- append = an index extension (reads both). bind = de-duplicate repeated values into one ability,
  with take-highest or count-total.
Risks and predictions:
- The header fill syntax (=x, +n, -n, +n>k, +n!k) is a small language. It needs a real
  tokenizer, tests and a defined error state. Edge cases: "+1>3!2" combos, negative starts, fills
  on a column whose row count changes, and "=fighter" in a column that also has manual edits
  (overwrite or skip?). Yellow state for syntax errors is in the spec.
- 40-row cap: the spec says yellow if a fill would exceed 40 rows. Today's career is hard-capped
  at 20 levels. Decide whether the matrix itself allows 21-40 (epic) or 40 is only a runaway
  guard.
- Color states: green = a value was found at that address, red = no index or no row for that
  count, yellow = syntax error or over cap. Prediction: tokens like "fighter4" vs a class literally
  named "Fighter4", and case/spacing ("Fighter" vs "fighter "), will cause false reds unless names
  are normalized.
- Count semantics: "fighter4" sets the count for that row without back-filling rows 1-3. Later
  plain "fighter" rows: do they continue at 5 or count only plain entries? The spec doesn't say,
  so this needs a decision.
- +bab/-bab/=bab+special filters depend on header names. If a user renames a header, filters
  silently stop matching, so headers need stable ids.
- * dominance (fighter,*wizard): wizard wins and fighter adds only the columns wizard lacks. The
  cell should stay green when this resolves.
- Spells: you flagged them as confusing and the spec stops there. Spells-per-day columns are
  numeric arrays per spell level, which the merge rules don't cover yet.
- Templates: marked work in progress in the spec. Leave them out of the first roadmap phase.
- Performance: recomputing a 20-40 row matrix on every keystroke is fine. Writing it to disk on
  every keystroke is not (see #3), so debounce the apply.

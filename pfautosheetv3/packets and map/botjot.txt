1. CURRENT STATE OVERVIEW
======================================================================
What it is
- "Pathfinder 1e Modular Workspace": a React 19 + Vite 8 + Tailwind 4 single-page app with an
  Express 4 server. It is an auto-calculating PF1 sheet (four sheet tabs) with a custom macro
  language ("Macaroni", v1.2 plus Part 2 rules) and many tools: Class Architect ("Add Class"),
  Point Buy, Buff Box, Dice, Deck, XDX, Macro Debug, Loadout, CMB, Journal, Image browser, and the
  AI Companion / Complete Sheet / Apple Eye. AI calls go server-side to OpenAI (gpt-4o-mini, then
  gpt-4o as fallback).

Which folder is live
- APP is the live codebase. gitstatus.txt: on main, up to date with origin/main. The only
  uncommitted change is "pfautosheet changes 11-18.txt".
- Newest code: src\engine\aiService.ts and macaroni\* (11-19). Newest docs: docs\program-map\*
  (11-21 7:34 AM).

Architecture
- APP\server.ts sets up Express on port 3000 (hardcoded). It loads .env then .env.local
  (server\env.ts) and mounts server\routes.ts:
    GET  /api/openai/status
    POST /api/openai/generate | /lookup | /complete-sheet  (same handlers also on /api/gemini/*)
    POST /api/sot/fetch-readonly-page  (fetches any http(s) URL the client sends)
  In development, Vite runs as middleware. In production (NODE_ENV=production) it serves dist\.
- Browser side: src\main.tsx -> StorageProvider -> CharacterProvider -> App.tsx.
  Character state is kept in three places:
    a) React state
    b) localStorage key pf1e_character_data_v1, rewritten on every edit
    c) optionally, a File System Access folder tree: <picked folder>\AIgamesheet\pfmusers\
       {player}\{character}\character.json, plus a Crash\ slot
- Installer path (installer\*.ps1) is separate. Start-PF1MW.ps1 serves a prebuilt standalone HTML
  on 127.0.0.1:38173 and does NOT run server.ts, so there are no /api routes and no AI there.

How to run the test server (from APP, in PowerShell)
  npm install            (or: npm ci)
  npm run dev            -> http://localhost:3000
  - "dev" and "start" are the same command: node --experimental-strip-types server.ts
  - Needs Node 22.6 or newer for --experimental-strip-types. Check with: node -v
  - Needs OPENAI_API_KEY in APP\.env.local for AI features. The file exists and contains that key.
    The app works without it, just with no AI. Check with
    http://localhost:3000/api/openai/status, which should show "configured": true.
  - Port 3000 is hardcoded. If something else is on 3000 (or a second copy is running), the server
    crashes with EADDRINUSE. It does NOT pick another port, even though the README suggests it will.
  - Handy URL switches from the code: ?stub=1 (in-memory fake storage with sample characters) and
    ?readonly=1.
Other scripts: npm test | npm run lint (tsc) | npm run build | npm run build:standalone |
  npm run dist:runtime (PowerShell packager) | npm run clean (uses "rm -rf", which won't work in
  Windows cmd).

2. FILE INGESTION - HOW FILES GET IN, AND WHERE IT BREAKS
======================================================================
There are four ingestion paths. All of them run in the browser. None runs on the server.

2A. SRD / SOT documents (.srd.json, .html, .txt, .md)
  Entry points:
   - AI Companion -> "Load SRD files" (accept=.json,.txt,.html,.md, multi-file)
     -> APP\src\components\tools\AICompanionModal.tsx handleImportHostSrdFiles (about line 763)
     -> APP\src\engine\sotEngine.ts parseImportedSrdFile()
   - Complete Sheet quick paste -> CompleteSheetChatWindow.tsx handleSaveQuickSot (pasted text only)
   - Weblink snapshot -> POST /api/sot/fetch-readonly-page (server strips tags, caps at 30,000 chars)
  Format expected for .srd.json: the app's own export format (exportSrdDocFileToHost):
     { "format":"PF1E_SOT_READONLY_SRD_V1", "exportedAt":..., "srdDocument": {
         id, title, category, htmlContent, plainText, isOverride, isReadOnly, tags,
         updatedAt, incidentalLinks[], securityAudit{}, hostSavedKey } }
   I checked this against APP\save tree test\armorist.srd.json and it matches exactly:
   title "armorist", htmlContent 198,025 chars, plainText 42,080 chars, 142 incidentalLinks.
   The parser also accepts a bare object with title plus plainText or htmlContent.
  What happens to it:
   1) sanitizeSrdDocument(): regex strip of scripts, iframes, forms, on* handlers and webhook URLs.
      <a> links become inert <span>s and are collected into incidentalLinks.
   2) saveSrdDocToHostDeviceStorage(): localStorage keys pf1e_host_srd_doc_<id> and
      pf1e_host_srd_index_v1.
   3) It is also pushed into character.sotCatalogue.overridePages, so it lives INSIDE the
      character: in localStorage pf1e_character_data_v1 and in the saved character.json.
   4) extractMacaroniSuggestionsFromSrd() runs regex patterns over the text and emits buff and
      macro suggestions.
  Failure modes and gaps
   - "format" is never checked. Any JSON with title plus text is accepted as an SRD.
   - A JSON file in some OTHER shape is NOT rejected. It silently falls through to "raw text", and
     the whole JSON string becomes the document's plain text. A structured file like
     {className, levels:[...]} would end up as one big text blob, with the category guessed from
     keywords. I could NOT inspect the pf1mod *.srd.json files (silvermind, technician, war priest,
     spheres of might, tinker sphere, divinitech pilot, suit pilot, gm house rules...). If they
     were exported by the app they will load fine. If they were hand-made or AI-made in another
     shape, they will load as text blobs. CHECK ONE before the run: it should start with
     "format":"PF1E_SOT_READONLY_SRD_V1".
   - No size limit and no quota handling. Each SRD is stored twice in localStorage, and browsers
     usually cap localStorage at roughly 5 MB per site. When it fills up:
       * saveSrdDocToHostDeviceStorage catches the error and returns '' (silent), but the UI still
         says "saved separately on host device!".
       * The character autosave in CharacterContext.tsx (line 180) has "ignore quota errors", so
         the sheet stops persisting with no warning.
     With 198 KB of HTML per SRD, a handful of class SRDs plus portrait images (stored as data
     URLs) will get there.
   - The folder save rejects character.json above 5 MiB (fsAdapter.ts MAX_FILE_BYTES, error
     FILE_TOO_LARGE). SRDs and images embedded in the character count toward that.
   - Every edit runs JSON.stringify on the whole character, SRD HTML included. Expect typing lag
     once a few SRDs are loaded.
   - Duplicates: re-importing the same .srd.json replaces it (same id). Pasting the same text
     again creates a new copy.
   - SRD originals never go into the save tree. fsAdapter only writes SRD\README.txt.
   - Hosts: HOST_SRD_* is per-browser localStorage, so Chrome and Edge, or port 3000 and the
     installer's 38173, each see a different set.

2B. Class data from an SRD -> Add Class (ClassArchitectModal, which is the one actually mounted)
   APP\src\engine\sotEngine.ts extractClassFromSrdDoc(), plus
   parseSrdSkillsAndProficiencies() in APP\src\engine\aiService.ts (about line 2347).
   I ran the same regexes on armorist.srd.json. Results:
   - Hit Die d10 found. "4 + Int" found. 20 progression rows matched.
   - BUG: the class-name regex /Table\s*:\s*([A-Z][A-Za-z\s'-]{2,25})/i lets \s eat newlines and
     tabs. The name comes out as "The Armorist\n\nLevel\tBase A". This only happens when the class
     name field is blank or "New Class". Typing the name first avoids it.
   - BUG: the "Special" column cleanup only strips plain trailing numbers. Spherecaster tables
     have "+0  +0 (1)  0 (+2)" style columns, so Special keeps them, for example
     "Bound equipment (+1), casting, spell pool, summon equipment\t+0\t+0 (1)\t0 (+2)".
   - Class skills are matched against the WHOLE document, not just the Class Skills line. For
     armorist that adds Fly and Heal (from "flying" and "healing"): 15 matched vs 13 real.
   - Hit dice: only d6/d8/d10/d12. Skill ranks: only 2/4/6/8 + Int. Homebrew like 3+Int or 5+Int
     won't be detected and defaults to 4.
   - If no table rows parse, it SYNTHESIZES a 1-20 grid from guessed BAB and save rates. It looks
     real, but it is invented.
   - Proficiency fallback: "Simple weapons, light armor." is used when nothing is found.
   - Hand-pasted grids (parseClassProgressionGrid, tabs or | or spaces) are covered by tests.
   - The old AddClassModal's "Populate from SRD" was gated by an AI blind-spot permission and fell
     back to sotDocs[0] (the wrong document) when no name matched. That modal is orphaned now, but
     check whether ClassArchitect's buttons behave the same way.

2C. Character sheet JSON (*_pf1e_sheet.json, loadouts, folder saves)
   - Sidebar Import: APP\src\utils\sheetExporters.ts importCharacterJSONFile requires
     parsed.name AND parsed.abilities to be truthy, then runs normalizeCharacterState().
     * A sheet with an EMPTY name ("") is rejected as "Invalid character sheet format", including
       a blank new character exported before you name it. PREDICTION: you will hit this if you
       export mid-creation and re-import.
     * A save-tree character.json (envelope: format / schemaVersion / sha256 / characterId / data)
       is rejected the same way. The sheet is under "data". Use Connect/Load for those, not Import.
   - Loadout ("Frankenstein") tool: LoadoutModal.tsx reads .json, auto-detects sections, and lets
     you merge them. CSV import is noted in the README as having issues.
   - Folder tree: APP\src\storage\fsAdapter.ts parseEnvelope() is strict. Format and schema
     version must match, sha256 must verify, at most 5 MiB, at most 64 levels deep, at most
     100k values. Keys that look like secrets (key, token, *apikey, *secret*, *password*, env...)
     are DROPPED silently on save and load. Normal sheet fields are safe (macroKey etc. don't
     match), but a custom object property literally named "key" or "token" would vanish.
   - normalizeCharacter() (APP\src\storage\characterState.ts) fills missing fields from a BLANK
     sheet. Old sheets load, but unknown fields pass through untouched.
   - Sample files: APP\default_sheet.json is LIVE (the Valerius demo used by "Reset to Iconic
     Demo"). Its xdxMacros use pre-1.2 syntax ("d20+#bab+#str ...", with no sigil).
     APP\New_Adventurer_pf1e_sheet.json and APP\save tree test\Valerius_the_Fireborn_pf1e_sheet.json
     are raw (non-envelope) sheets that nothing reads. The pf1mod Hanzo/Kirin/test_character
     _pf1e_sheet.json files are presumably the same raw format (not verified).

2D. Images: data URLs stored in the character and in localStorage pf1e_image_library_v1. They
    count toward the same quota and the 5 MiB limits.

  character.json / active.json (fsAdapter.ts lines 14-18).

LAZY\sheet-engine vs APP ingestion (the "is it the new engine?" question)
- It is a Node-only (fs + cheerio + MiniSearch) deterministic indexer plus a step-by-step build
  state machine. It is designed to replace server\sotContext.ts and the full-SOT prompt
  (integration\sotContextAdapter.ts). It has never been wired in. APP has no reference to it.
- It reads .html/.htm/.md/.txt ONLY (ingest.ts SUPPORTED_EXT). I tested it on a folder containing
  armorist.srd.json plus the same SRD saved as .html. The .srd.json was skipped silently. The HTML
  became 114 sections and 2 tables, and estimated tokens dropped from 49,517 to 11,187 (-77%).
  links=0, because APP's sanitizer had already turned the <a> links into spans.
- Its README describes the CURRENT sotContext.ts as "keyword excerpts from the last 4 messages,
  12k cap". The real APP\server\sotContext.ts sends every page's full plainText with no cap. It was
  written against a different or older version of that file, so the integration notes need
  refreshing.
- To merge it, you would need: an /api endpoint that runs ingest server-side (SRDs currently live
  in browser localStorage), a .srd.json -> HTML unwrap step, and an alignment pass (TS 5 + vitest
  vs APP's TS 7 + node:test).
- Verdict: a component to merge into APP's server layer, not a replacement app. Keep it.

3. LIKELY FUTURE OBSTACLES / RISKS
======================================================================
- Token cost and rejections: Complete Sheet sends the full text of all SOT docs, plus history,
  every turn (aiService.ts about line 3034 sends all overridePages; sotContext.ts has no cap).
  armorist alone is about 42k chars (roughly 10k tokens). Five to ten homebrew SRDs gets close to
  gpt-4o-mini's context window, and falling back to gpt-4o makes rate limits worse. This is
  SKEL\the problem.txt, still open.
- Storage ceilings: localStorage quota (silent), the 5 MiB character.json limit, and SRDs stored
  twice. This gets worse as you add the pf1mod data set.
- Startup trust order (from docs\SAVE_STATE_DIAGNOSIS.md, confirmed still true by
  docs\program-map\05): localStorage paints first, a Crash snapshot with a different checksum wins
  over the named save, and saveCharacter doesn't refresh Crash.
- Macro syntax drift: Macaroni 1.2 / Part 2 rejects leading #, $, >> and ^. Still emitting the old
  "Name:|<^...>|$" syntax:
    sotEngine.ts line 510 (SRD-derived AC buffs)
    aiService.ts lines 195, 219, 425-849 (built-in feat and spell suggestions: Dodge, Haste,
      Mage Armor...)
  The Valerius demo xdxMacros have no sigil. The README "Tools" section still teaches
  "#objectname or {objectname}".
- Duplicate class tools: ClassArchitectModal (mounted) and AddClassModal (orphaned) each have
  their own copy of the SRD-populate logic. Fixes made to one won't reach the other.
- /api/sot/fetch-readonly-page fetches any URL with no allowlist, and /api has no auth. Fine on
  localhost; a risk if it's ever hosted.
- Installer and packager mismatch (per docs\PROGRAM_MAP.md): Package-PF1MW.ps1 includes files
  that Install-PF1MW.ps1 rejects, and Install-PF1MW-Local.ps1 skips files that Start-PF1MW.ps1
  needs. The installed app has no AI because there is no server.
- Naming leftovers that confuse agents: package name "react-example", /api/gemini/* calling
  OpenAI, metadata.json still saying "SERVER_SIDE_GEMINI_API", the README saying Gemini errors
  may appear.
- Tests: no coverage for pf1eMath, multiclassCalculator, career math, React, or the SRD class
  extractor. The macaroni tests exist but aren't in "npm test".
- Node: dev relies on --experimental-strip-types (Node 22.6 or newer). The release CI uses
  Node 22, so check that your PC matches.
